## Part 1. BPE Tokenizer

The BPE tokenizer is fundamentally a data-driven compression algorithm over bytes. Initializing the vocabulary with special tokens first and then all 256 byte values is not an implementation detail but a correctness guarantee: it ensures that any UTF-8 string can be represented losslessly, while still allowing higher-level units (subwords, morphemes, whole words) to emerge naturally during training. The dual maps stoi and itos exist to make this bidirectional mapping explicit and cheap, which later becomes critical for both fast encoding and deterministic decoding.

### Why Pretokenization Exists Before BPE

Pretokenization is not meant to tokenize in the linguistic sense, but to limit the search space of merges. By splitting text into stable "word-like" byte spans using a GPT-2–style regex, BPE avoids learning merges that cross obvious semantic or syntactic boundaries such as whitespace or punctuation. Special tokens are deliberately extracted and isolated at this stage so that they remain atomic and immune to merges; this prevents corruption of control symbols like `<|endoftext|>` during training.

### Why Naive BPE Training Is Too Slow

The brute-force BPE algorithm is conceptually simple but computationally pathological. Recounting all adjacent token pairs after every merge and rewriting the entire token sequence each time leads to quadratic behavior. This is why a naive implementation can pass correctness tests but fail speed tests by orders of magnitude. The real insight is that most of the token sequence does not change during a merge; only the local neighborhood around merged pairs is affected. Any efficient implementation must exploit this locality.

### Data-Structure-Driven Optimization Insight

The optimized solution reframes BPE as a dynamic graph problem rather than a sequence rewrite problem. A doubly linked list represents the current token stream so that merges become pointer updates instead of array copies. Pair frequencies are tracked once and updated incrementally, while a max-heap ensures that the globally best merge candidate is always accessible. Crucially, the heap is updated lazily: outdated entries are allowed to exist and are discarded only when popped. This avoids expensive heap surgery and keeps the algorithm fast in practice.

The custom heap ordering encodes the BPE merge rule directly: frequency dominates, with byte-wise lexicographic order used only to break ties. This preserves exact BPE semantics while still enabling O(log n) selection of the next merge.

### Encoding, Decoding, and Memory Awareness

Encoding reverses training logic: it greedily applies the earliest learned merge until no applicable pair remains. Using fixed-width arrays instead of Python lists is not an aesthetic choice but a memory safeguard—token streams can be extremely long, and per-token overhead matters. Special tokens are matched first and by descending length to avoid accidental partial matches, which is a subtle but critical correctness constraint.

Decoding is intentionally trivial. Because BPE never loses byte information, decoding reduces to concatenating byte sequences and performing a single UTF-8 decode. The simplicity here is a sign that the invariants were preserved during training and encoding.

### Serialization as a Consistency Contract

Serialization is not just about saving state; it is about freezing the exact merge order. Since BPE behavior depends entirely on merge ranking, restoring merges_rank and pair2new precisely ensures that a deserialized tokenizer behaves identically to the original. This guarantees reproducibility across machines, runs, and deployments.
